# AI開発者へ：Expediaが годы前に学んだ「スケーラブルなAIシステム」の教訓

AI業界が自律型エージェント的时代に入る中、旅行テック大手のExpedia Groupは、数年にわたるAI・機械学習の实战経験）から得た原則を公开发表した。本稿では、ExpediaのVP Xavi Amatriain氏が語った「スケーラブルなAIシステム構築」の实践经验と教訓を整理する。

---

## AIは「動く」だけでなく「scale」する必要がある

Expediaの教训の核心はシンプルだ：**「今日動くAI」と「scaleするAI」は别物である**。

多くの企业在「最初の1回动作する」ことに集中し、`scale`するかどうかの检讨を怠る。Velocity（速度） without discipline（规约）や戦略的な方向성은、资产ではなく负债になる。

Expediaは以下领域でAI/MLを活用してきた：
- **パーソナライゼーション**：旅行者の行动履历に基づく推荐
- **ランキング**：検索結果の最適化
- **不正検出**： antifraudシステム
- **カスタマーサポート**：自动応答
- **生成AI・エージェントAI**：最近の领域

この深度の经验が、「ML/AI原则」を社内で策定する动機になった。

---

## エージェントAI時代の「Agentic Release」門番

Expediaが 开発した注目すべき概念が「**Agentic Release Tollgates（エージェント解放の门番）**」だ。エージェントAI機能をローンチする前に必须のチェックリストで、以下の原则を具体化している：

- **明確な所有権**：谁が责任を持つのか
- **リスクベースガバナンス**：リスクしベルに応じたプロセス
- **評価（Evals）**：モデルの性能测定
- **安全ロールアウト**：段階的デプロイ
- **モニタリング**：プロダクションでの継続监视

これらのチェック項目は既に**SDLC（ソフトウェア开発ライフサイクル）に自动化・統合**されつつある。将来的には、AIシステムの设计・評価・承认・ローンチ・监视が最初から組み込まれることを目指す。

## 成果：实际に重要なことを測定する

### 1. ビジネス成果に连动させる

すべてのML努力は、**关键业务成果または旅行者体験メトリクスに直接接続**되어야 한다。技术的な最適化は中间目的であり、最终目的ではない。

### 2. コスト対効果の最適化

モデルの価値は、开发・训练・监视のコストと、そのもたらす運営复杂度を加えたものを正当化しなければならない。**ROI（投資対効果）を常に意识する**ことが重要。

### 3. 复杂さには正当な理由が必要

新しいモデルやアーキテクチャ導入时に确认すべき問い：「**単純なベースライン（既存の了一般モデル、简单な启发的アプローチ、市贩ソリューション）では不十分なのか？**」复杂さは「赢得」するもの。最初に简单な解法尝试し、本気で必要だと证明されてから专业化へ進む。

### 4. オフライン＋オンライン評価の并行

プロダクション展开の判断には、**オフライン評価だけでなくオンライン評価も必要**。片方だけで判断しない。オフライン評価がオンライン结果を予測できるようになることが目标。

## 设计：チームを超えてscaleするシステム

### 共享基盤の重视

Expediaが最も强调するのは「**共有基盤の构筑**」だ。

-  핵심能力・データ表現・モデル構成要素は**全社共有の基盤**として构筑
- 专业化（specialization）はその基盤の上に构筑
- 基盤が改善되면、组织全体に利益が流れる

この逆で、异なるチームごとに个別のスタックを構築すると、改进がサイロ效应で閉じてしまう。

### データは第一級の制品

「**モデルの品質はデータの品質に制约される**」。这句话은MLにおいて永远の真理。

Expediaは以下の要件を明确规定：
- **堅牢なパイプライン**：データの流れが安定
- **明確な系列（Lineage）**：データの出所を常に追踪
- **再現可能性**：同じ条件で再训练可能
- **文書化された所有権**：谁が责任を持つのか明確
- **明確なスキーマとSLA**：他のチームが依赖できる保证

### 「局所最適化」よりも「一般性」を優先

2つのアプローチが类似した性能の場合、**他のチーム・ブランド・ユースケースに再利用できる方を优先**する。ローカルな性能だけでなく、改进が社内でどのくらいの速さで広がるかも最適化の对象。

### 手作业のビジネスルールは最小化・sungdown

手作业ルールは政策・安全・合规性のために必要がある场合もあるが、常に**明確な文書化と定期的レビューが必要**。弱いモデルのパッチや恒常的なメンテナンス负债の源になってはならない。

### 再现性と追跡可能性はデフォルト

训练データ、features、设定、評価结果、デプロイバージョン、关键的な意思決定は**すべて文書化され復元可能**である必要がある。これにより、 生产環境で数ヶ月後に问题が发生してもデバッグでき、引き継ぎ時に組織の知识が失われることを防ぐ。

## 開発者への教训まとめ

| 原则 | 実践 |
|------|------|
| ビジネス成果に连动 | 技术指标だけでなくビジネスKPIで测定 |
| コスト対効果の最適化 | ROI计算的を常に実施 |
| 简单さから复杂へ | 強いベースラインから开始し、必要に応じて专业化 |
| オフライン＋オンライン評価 | 两方の視点でモデルを验证 |
| 共有基盤の构筑 | サイロを避け、改进が全社に流れる架构 |
| データは第一級 | データ品质への投资を惜しまない |
| 一般性の优先 | 再利用可能な设计を心がける |
| 手作业ルールの最小化 | ルールは明示的にし、定期クリーンアップ |
| 再现性の确保 | 文书化とバージョン管理をデフォルトに |
